# 谁听见定下之后，有 key 时读句进 Agent Loop

用户输入不受控。先定谁听见（职业主对话 implicit，项目里没 @ 只有主成员，今日无 @ 时看口令 Trigger）。有 key 时：零歧义写口令（芯片原句，或口令开头带参数，如「开实验 官网 CTA」）仍走固定 bridge；读 Skill、模糊写句和赋能建议交给该成员的 dsh session，人设里带本职工具目录与 Skill 合同。无 key 时才用 Trigger 家族匹配兜底。空白助手本身就是对话，不再套一层分配。今日无 @：唯一口令唤对应成员；问句请 @ 或再说口令，不拆待办；其余才拆成待办。不做全局模型派职业。

## 为什么这样

正则和问句启发式只能覆盖词表里的说法。身份、模型、解释和没写进 Trigger 的口语，必须进 Agent Loop 才能调工具完成工作。写 Skill 仍要求明确口令才走 bridge，避免提到相关词就入账或转稿。赋能建议不再另开 `skillChat` 入口，说明书写进人设。今日是收件箱，默认收待办；但「刷新态势」已经是口令，问「增长如何」也不是一条待办——这两类不该被默默拆进日程。今日 Trigger 只用芯片原句 / 写口令快路径，不用职业宽正则，所以「今天的产品 idea 是什么」不会按评估 Skill 抢走待办，而是当问句请用户 @ 选品策略师。

## 考虑过但没选

- 只在 miss 后再猜一次：对上 Trigger 的句子仍绕过模型，身份问句会被词表挡掉。
- 全局先识别再派职业：今日里的「今天的产品 idea」会抢走「拆成待办」。
- 组合模板摊平账号+弹药 Skill：中栏会抢词。雇佣「自媒体运营达人」拆成两个左栏身份；遗留的摊平实例只按主 Panel（账号）匹配。
